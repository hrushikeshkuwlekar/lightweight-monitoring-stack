🎯 Fixed Rate (open model)

You choose the TPS. Requests start on schedule whether or not earlier ones have finished; users are added as needed. Like real internet traffic — and k6 constant-arrival-rate.

👥 Fixed Users (closed model)

You choose the number of users. Each sends a request, waits for the answer, thinks, repeats. TPS is the result — like JMeter thread groups.

📘 How it works — the concepts in one page

1. Little's Law

TPS = users ÷ (response time + think time). Equivalently in flight = TPS × response time. If the app answers faster, the same users produce more TPS; if it slows down, TPS drops.

2. Two ways to drive load

  • Fixed Users (closed model) — you set users; TPS is the outcome. When the app slows down, TPS drops automatically because users wait longer for answers. Hides problems from you if you only look at errors.
  • Fixed Rate (open model) — you set TPS; users are the outcome. When the app slows down, more requests pile up in flight. If they exceed max users the generator must skip requests — it can't keep up.

3. Is it the app, or the load generator?

Generating load costs CPU. If the generator runs out, it sends late and measures late, so the app looks slow when it isn't. Always check generator CPU before blaming the app.
